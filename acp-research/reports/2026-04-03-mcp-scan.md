## MCP 最新动态

### 最新版本：2025-06-18

MCP 规范于 2025-06-18 发布了最新稳定版本（基于 `modelcontextprotocol.io/specification/2025-06-18`），是截至本轮扫描的最新版本。这是一次涵盖**安全性增强、功能补完与规范简化**的重大更新。

### 最新 Commits（关键变更概要）

| 变更 | 描述 | 影响 |
|------|------|------|
| **移除 JSON-RPC 批处理支持** | Streamable HTTP 传输实现中未发现批处理实际需求；通知/响应模型难以满足实时性和并发调用需求 | 规范简化，降低实现复杂度 |
| **结构化输出（Structured Output）** | 工具调用结果新增 JSON Schema 验证，支持结构化数据返回 | 大幅提升 Tool→Agent 数据可靠性 |
| **Elicitation 机制** | Server 可在工具执行过程中向用户请求结构化输入（嵌套式交互） | 支持多轮交互工作流 |
| **更严格的版本协商（Version Negotiation）** | 强制版本兼容检查，避免协议版本漂移导致的静默失败 | 提升协议稳定性 |
| **OAuth 安全增强** | 强化 OAuth 2.0 集成规范，改进 token 管理 | 降低未授权访问风险 |

### Open PRs 与 Issues（截至扫描时）

- **Elicitation 是 2025-06-18 最受关注的新特性**，允许服务端在 Tool 执行中途发起用户交互，打破了传统"单向调用"模型

### 关键发现

1. **MCP 向"双向交互"演化**：Elicitation 机制将 MCP 从纯粹的"单次 Tool 调用"推向了带状态的交互流，这与 ACP 的消息流模型产生了概念交叉点。

2. **MCP 正在成为行业事实标准**：Cisco、AWS（Kiro）、腾讯、ModelScope 均在 2025 年深度集成 MCP，生态极为活跃。

3. **ACP×MCP 双协议实践已有先例**：AWS Kiro + OpenClaw 已实现 MCP+ACP 双协议协作架构（见下文），这是目前已知最具参考价值的生产实践。

## ACP × MCP 互操作分析

### 定位对比

| 维度 | MCP | ACP |
|------|-----|-----|
| 通信模式 | Agent↔Tool（LLM 调用外部工具） | Agent↔Agent（P2P 协作） |
| 拓扑 | Client-Server（单向发起） | P2P / Hub-Spoke |
| 协议层 | Tool invocation（JSON-RPC 2.0） | Message passing（结构化消息） |
| 标准化程度 | 高（Anthropic 主导，行业广泛采纳） | 中（开放，轻量，尚在演进） |
| 状态性 | 无状态（2025-06-18 前）→ 开始支持带状态交互 | 天然有状态（消息队列，轮次管理） |
| 发现机制 | 无内置 / 依赖配置 | Agent 能力广播（skill 注册） |
| 安全模型 | OAuth 2.0 + HTTPS | 待强化（认证机制相对弱） |
| 典型用途 | 文件读写、数据库查询、API 调用 | 多 Agent 协同、任务委派、工作流编排 |

### 互操作场景分析

#### 场景 1：MCP Server 作为 ACP Agent 的技能来源（MCP Tool → ACP Skill）

**描述**：ACP Agent 将 MCP Server 包装为一个 Skill，通过 ACP Skill 接口暴露 MCP 提供的工具能力。

```
ACP Agent
  └── Skill: "file-manager"
        └── [内部实现] MCP Client → filesystem MCP Server
  └── Skill: "web-search"  
        └── [内部实现] MCP Client → brave-search MCP Server
```

**价值**：
- ACP Skill 生态可直接复用庞大的 MCP Server 生态（已有数千个 MCP Server）
- 无需重新实现工具层，ACP 专注于 Agent 协作逻辑
- 实现路径清晰：ACP Skill 的 `execute()` 方法内部调用 MCP Client

**实现复杂度**：低～中（主要是适配层开发）

---

#### 场景 2：ACP Agent 通过 MCP 暴露自身能力（ACP Agent → MCP Server）

**描述**：ACP Agent 同时作为 MCP Server 运行，将自身的 Agent 能力（推理、规划、多步执行）通过 MCP Tool 接口暴露给 MCP 生态中的其他客户端。

```
MCP Client（如 Claude Desktop、Cursor）
  └── Tool: "run_agent_task"
        └── [内部] ACP Agent（处理复杂多步任务）
              ├── 子任务分发
              ├── 其他 ACP Agent 协作
              └── 返回结构化结果
```

**价值**：
- 允许现有 MCP 用户无缝调用 ACP Agent 的复杂推理能力
- ACP 可作为 MCP 的"能力增强层"——MCP 擅长原子操作，ACP 擅长编排
- 2025 年 AWS Kiro + OpenClaw 实践：**Kiro 通过 MCP 调用 OpenClaw 触达外部世界，OpenClaw 通过 ACP 委派 Kiro 完成深度代码生成与架构分析**，已在生产中验证

**实现复杂度**：中（需要 ACP Agent 实现 MCP Server 接口）

---

#### 场景 3：ACP Bridge for MCP — 混合编排层

**描述**：设计一个专用的 ACP-MCP Bridge，统一管理 MCP Tool 调用与 ACP Agent 委派，提供统一的任务路由能力。

```
任务入口（自然语言）
  └── ACP-MCP Bridge Agent
        ├── 原子任务 → MCP Tool（直接调用）
        ├── 复杂任务 → ACP Agent（委派执行）
        └── 混合任务 → 并行/串行编排
```

**价值**：
- 消除"用 MCP 还是用 ACP"的决策负担，由 Bridge 自动路由
- 统一错误处理、重试、超时语义
- 为 ACP 生态提供"向下兼容 MCP"的能力入口

**实现复杂度**：高（需要意图分类 + 协议适配 + 编排逻辑）

### 可行的集成方向（优先级排序）

#### 🥇 P1：ACP Skill Adapter for MCP（立即可做）

在 ACP Skill 标准中增加 `mcp_server` 配置项，允许 Skill 声明自己由某个 MCP Server 提供支持，并由 ACP 运行时自动处理 MCP 客户端生命周期。

```yaml
# skill.yaml 示例扩展
name: filesystem
type: mcp_backed  # 新增类型
mcp:
  server: uvx mcp-server-filesystem
  transport: stdio
  tools:
    - read_file
    - write_file
    - list_directory
```

**好处**：
- 零成本接入 MCP 生态的数千个 Server
- Skill 开发者无需写 MCP 客户端代码
- ACP 运行时统一管理 MCP Server 进程

#### 🥈 P2：ACP Agent 暴露为 MCP Server（中期规划）

为 ACP Agent 提供 `--serve-mcp` 启动选项，自动将 Agent 的已注册 Skill 映射为 MCP Tool 列表，使任何 MCP Client 均可调用 ACP Agent 能力。

```bash
# 启动 ACP Agent 同时作为 MCP Server
acp-relay run --serve-mcp --port 8765
```
