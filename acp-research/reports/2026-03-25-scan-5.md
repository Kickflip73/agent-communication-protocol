## 🔴 A2A Issue #1685：错误响应 Content-Type 未定义

**问题：**
A2A spec 未明确错误响应的 Content-Type：`application/json` 还是 `application/problem+json`？

- PR #1600 将 Google AIP-193 错误格式替换了原 RFC 9457，同时意外删除了 `application/problem+json` 的说明
- Spec 中仍有 2 处例子用了 `application/problem+json`，与正文矛盾
- 社区无法确定标准

**ACP 现状：✅ 无此问题**
- `_json()` 方法统一所有响应（含错误）用 `application/json; charset=utf-8`
- 无任何位置使用 `application/problem+json`，Content-Type 一致，零歧义
- 可在 spec/README 中明确记录这一设计选择，作为差异化优势

**Action item（低优先级）：** 在 spec 中显式注明 "All responses including errors use `application/json`"

## 🟠 A2A Issue #1681：Push Notification 配置 API 泄露凭证（安全漏洞）

**问题：**
`GetTaskPushNotificationConfig` / `ListTaskPushNotificationConfigs` API 在返回推送配置时，将 credentials（认证凭证）明文包含在响应中，造成敏感信息泄露。

**ACP 现状：✅ 不受影响**
- ACP webhook 仅存储 URL（`_push_webhooks = []`），无 credentials 字段
- Webhook 注册（`/webhooks/register`）只接受 URL，无认证信息，设计上规避了此问题
- ACP 的极简设计（P2P + URL-only webhook）天然避免了 OAuth/凭证复杂性
