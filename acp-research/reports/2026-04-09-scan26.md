## 新发现 Issues（本次首次跟踪）

### A2A #1723 — SLIMRPC 协议绑定提案（Tehsmash / Agntcy）
- **提案者**：Tehsmash（Agntcy 组织）
- **摘要**：在 A2A 下建立 `experimental-cpb-slimrpc` 仓库，支持 SLIM（Secure Low-Latency Interactive Messaging）网络层上的 RPC 绑定
- **SLIM 核心特性**：
  - Agent 用三层结构名（`namespace/group/name`）寻址，非 URL/端口
  - 网络层内置身份管理，无需应用层 Auth header 或 TLS 证书
  - 适合 NAT 后、无固定 IP 的边缘环境和多 Agent Mesh 部署
- **对 ACP 的启示** ⚡：
  - SLIM 的「名称寻址而非 URL 寻址」方向与 ACP P2P 理念正交——ACP 用 IP+Token，SLIM 用名称+Broker
  - ACP 可考虑在 v2.x 后期支持「Named Endpoint」作为可选寻址方式（长期）
  - SLIM 网络层身份管理思路值得借鉴——减少应用层负担
- **优先级**：P3（观察，不追踪实现）

## 重要信号：身份认证生态动态

### A2A #1712 — WTRMRK + Multi-provider Identity（64R3N 主导，aeoess 关键评论）
- **核心观点（aeoess）**：
  > "rather than A2A picking one [identity system], the protocol would benefit from an identity verification extension that accepts multiple providers"
  - 支持多 provider：WTRMRK/SATP/AgentID/APS/Ed25519
  - 关键评论：**Ed25519 已成 agent 生态实际标准**（APS、AgentID、SATP、IETF draft-prakash-aip 均用 Ed25519）
  - "RSA signatures work but Ed25519 is becoming the de facto standard"
- **对 ACP 的直接利好** ✅：
  - ACP v2.85 Ed25519 默认开启 + `POST /identity/verify-card`——这正是 aeoess 描述的「multi-provider 方向」的实践
  - aeoess 认为关键三层：**身份（who）+ 委托范围（what they can do）+ 执行证明（what happened）**
  - ACP 三层均已实现：Ed25519（身份）+ capability_token/effective_tier（委托）+ interaction_records（执行证明）
- **行动建议**：可在 #1712 评论中引用 ACP 方案，展示三层实现 → 扩大社区影响力
- **优先级**：P1（v2.93 行动项）

### A2A #1713 — OBO 跨组织委托标准（kevin-biot）
- **核心问题**：两个 Agent 首次接触、无共享 AS、跨组织时如何建立信任？
- **四大缺口**：
  1. Principal authority chain（谁授权了这个 Agent？）
  2. 跨组织首次接触认证（无共享 AS 时 OAuth 不可用）
  3. 防篡改的事后证据（可离线验证）
  4. 法律实体问责（谁对损害负责？）
- **对 ACP 的启示** ⚡：
  - ACP `principal_chain`（v2.56）已解决问题 1（OBO 委托链）
  - ACP `interaction_records` 双边签名（v2.61）已解决问题 3（防篡改证据）
  - 问题 4（法律实体）超出协议范畴，但可在 governance_metadata 中声明 `legal_entity` 字段（长期）
  - **关键差距**：问题 2（跨组织首次接触认证）——ACP `POST /identity/verify-card` 支持无预连接验签，部分解决，但没有「多个 Agent 共同见证初次接触」的机制
- **行动建议**：评估 `principal_chain` + `verify-card` 组合能否完整覆盖 OBO Pattern 2
- **优先级**：P2（v2.93 研究方向）
