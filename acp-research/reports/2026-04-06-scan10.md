## 核心架构变化：三层规范结构

A2A v1.0.0 引入了 **三层协议架构**（重大重构）：

```
Layer 1: Canonical Data Model (Proto)
  Task / Message / AgentCard / Part / Artifact / Extension

Layer 2: Abstract Operations
  SendMessage / StreamMessage / GetTask / ListTasks / CancelTask / GetAgentCard

Layer 3: Protocol Bindings
  JSON-RPC | gRPC | HTTP+JSON/REST | Custom Bindings
```

### 关键变化对 ACP 的影响
1. **gRPC 绑定正式化**（Layer 3）— A2A 官方支持 gRPC，ACP 继续走 HTTP-only P2P 路线，差异化优势保留
2. **Proto 成为规范源**（`spec/a2a.proto`）— JSON Schema 是构建产物，不再手工维护；ACP 继续用 OpenAPI YAML，定位不同
3. **Extension 机制正式化**（Layer 1 新增）— ACP 的 capabilities/skills/limitations 扩展字段方向对齐

## 核心操作（v1.0.0 spec）

| 操作 | 说明 |
|------|------|
| `SendMessage` | 发消息，返回 Task 或直接 Message |
| `SendStreamingMessage` | 流式发消息，SSE 推送 TaskStatusUpdateEvent/TaskArtifactUpdateEvent |
| `GetTask` | 获取 Task 状态（支持 historyLength） |
| `ListTasks` | 列表 + 过滤 + 分页 |
| `CancelTask` | 取消 Task |
| `GetAgentCard` | 获取 AgentCard 元数据 |

### Task 终态（spec 明确）
- `completed` / `failed` / `canceled` / **`rejected`**（新增）
- 发消息给 terminal-state Task 返回 `UnsupportedOperationError`

### Message vs Task 二元响应
- **简单交互**: 直接返回 `Message`（无 Task 开销）
- **复杂异步**: 返回 `Task` + SSE 流

## ACP 对比分析

| 特性 | A2A v1.0.0 | ACP v2.65.0 | 分析 |
|------|-----------|-------------|------|
| 规范源 | Proto (.proto) | OpenAPI YAML | ACP 更轻量，易读性好 |
| 传输 | HTTP/gRPC/JSON-RPC | HTTP-only（P2P relay） | ACP 无中心服务器 |
| Task 终态 | 含 `rejected` | 未含 `rejected` | **需考虑对齐** |
| 二元响应 | Task 或 Message | 仅 Task | ACP 可考虑加 direct-message 模式 |
| Extension | 官方 Extension 类型 | capabilities/limitations | 方向一致 |
| 身份 | 未在 spec 中心化 | Ed25519 + DID | ACP 更强 |
| P2P | 不支持 | 核心特性 | ACP 差异化定位 |

## 对 ACP v2.66 的建议

### 高优先级对齐
1. **Task 状态 `rejected`** — 与 A2A v1.0.0 对齐，当 agent 主动拒绝 task 时使用
2. **`direct_message` 支持** — `SendMessage` 可直接返回 Message（无 Task 创建），降低简单交互开销

### 中优先级跟进
3. **Extension 字段声明** — `/agent-card` 中加入 `extensions[]` 声明
4. **`historyLength` 参数** — `GET /tasks/{id}` 支持 historyLength 过滤历史消息数量

### 低优先级（不对齐，保持 ACP 差异化）
5. gRPC — ACP 坚持 HTTP curl-friendly，不引入 gRPC
6. Proto 规范源 — 继续用 OpenAPI YAML，对个人/小团队更友好
