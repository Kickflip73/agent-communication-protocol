## 重点新发现

### 🆕 Issue #1716 — A2A Skill Authorization RFC（今日新开）

**核心内容：**
A2A 正式承认 AgentCard `SecurityRequirement` 只解决了"认证（authentication）"，没有解决"授权（authorization）at skill boundary"。SINT Protocol 被引用为候选补充方案。

RFC 提案的 Tier 系统与 ACP 惊人相似：
- T0/T1: auto-execute（低风险/只读）
- T2: operator approval（有后果的操作）
- T3: human sign-off before execution（不可逆：金融/物理/基础设施）

**ACP 差异化优势（可在文档中明确）：**

| 特性 | SINT Protocol（A2A #1716 提案） | ACP v2.49-v2.51 |
|------|-------------------------------|-----------------|
| 授权 Tier | T0-T3（Ed25519 capability token） | T0-T3（trust score + verified_identity） |
| 参数约束 | constraints 字段（token 内嵌入） | `skill.param_constraints`（AgentCard 内声明） |
| 不可逆任务确认 | T3 human sign-off（机制未指定） | `human_confirmation_required` + `:confirm`/`:reject` 端点 |
| 实现方式 | 外部 AS + Ed25519 token 颁发 | **零外部依赖**，relay 内置 trust 计算 |
| 复杂度 | 需要 SINT AS、token 管理、PKI | 2 个字段 + 3 个端点，curl 可接入 |

**战略意义：** A2A 社区正在从 0 讨论我们 v2.49-v2.51 已经解决的问题。ACP 有机会成为**轻量 Authorization 层的参考实现**。

### 🆕 Issue #1713 — OBO（On Behalf Of）跨组织问责层

**核心内容：**
OBO 试图解决"两个 Agent 首次接触、无共享 AS、跨组织场景"的问题：
1. 委托权威链（谁授权给这个 Agent？）
2. 跨组织首次接触认证
3. **不可篡改的任务后证据**（post-task evidence）

**ACP 视角：**
- 委托权威链：ACP vouch_chain（v2.14 trust.signals）已有基础，但没有强制 principal chain
- **不可篡改任务后证据 → 与 ACP v2.52 audit_log 高度对齐！**
  - ACP audit_log 是 append-only，seq 单调递增，记录完整生命周期
  - OBO 提案的 "tamper-evident terminal task states" 本质上与 audit_log 解决同一问题
  - **ACP 已领先实现，且比 OBO 更详细（事件级而非仅终态）**

## v2.53 候选特性

基于本轮扫描，以下特性值得跟进：

### 候选 A：`POST /verify-card` — AgentCard 签名验证端点
- **背景**：#1672（292 评论）是 A2A 最热 issue，今日再次活跃
- **ACP 基础**：JWKS（v2.18）+ `verified_identity` signal + `card_sig` trust signal 已有基础
- **实现思路**：接收一个 AgentCard JSON + 其 JWKS URI，验证 `card_sig` 字段的 Ed25519/RS256 签名
- **价值**：让 ACP 成为可验证 AgentCard 的独立工具，差异化于 A2A（A2A 还在讨论要不要加）

### 候选 B：`task.principal_chain[]` — 委托权威链
- **背景**：OBO #1713，解决"谁授权给 Agent"的跨组织场景
- **ACP 基础**：vouch_chain trust signal 有雏形
- **实现思路**：task 对象增加 `principal_chain[]`，记录每层委托（AgentCard URI + sig）
- **复杂度**：较高，需要 PKI 基础或 DID 支持

### 候选 C：`skill.rate_limit` — 调用频率限制
- **背景**：生产级防滥用需求，当前 ACP 没有任何限流机制
- **实现思路**：`{requests_per_minute, requests_per_day, burst}`，`POST /tasks` 超限返回 429 ERR_RATE_LIMIT
- **复杂度**：低，in-memory 计数器即可
- **差异化**：A2A 完全没有这个，简单实用

### 推荐下轮开发：**候选 C（skill.rate_limit）**
- 实现成本低，测试覆盖容易
- 生产价值明确（防滥用）
- 与现有 authorization_tier 机制形成互补（tier = 谁能调，rate_limit = 调多少次）
